# 概要设计检查维度

[最终内容要求](content-checklist.md)用于检查内容覆盖情况及设计深度；本页的 D01—D17 用于给问题分类并判断影响，不是另一轮全量检查。同一根因跨领域只计一次。所有维度先判断是否涉及结构性、全局性决定或项目明确的本阶段交付要求；局部实现细节缺失不自动构成问题。

按系统类型和本次设计阶段裁剪；本清单是建议框架，用户明确的约束和提供的适用标准优先。信息不足时标明未知，不按高复杂度交易平台的要求一律检查所有系统。

| ID | 维度 | 具体审查与可检验问题 |
|---|---|---|
| D01 | 完整性与范围 | 本期/远期、现状/目标、整体/专题、视图及未决项是否清晰；应在本阶段承担的结构性、全局性内容是否覆盖，不以章节名称或顺序判断。不能因专题文档未重复其他专题而判缺漏。 |
| D02 | 需求与约束覆盖 | 可追踪的关键业务/非功能需求是否有概要方案响应；重要功能是否遗漏，实时目标是否被次日批量替代，既有约束是否被忽略；矛盾目标先列冲突。功能的具体分配见 D15。 |
| D03 | 边界与职责 | 业务能力、模块、系统、所有者及依赖是否明确；是否存在多个未经协调的权威来源、无人承担职责、循环依赖或绕过边界。分层不是一律越多越好。 |
| D04 | 流程与接口 | 端到端的成功、拒绝、超时等处理路径是否完整，同步与异步交互语义、接口约定、错误处理及最终结果的获取方式是否明确。异步受理不等于最终成功。 |
| D05 | 概念数据与生命周期 | 核心实体、标识、关系/基数、权威归属和生命周期是否支撑主流程；副本复制/同步、质量、归档/删除是否明确。以明确留存要求为准，不发明法定年限；物理拆表或缺少列定义不自动属于概要设计缺漏。 |
| D06 | 事务与一致性 | 原子性范围、部分成功、重试、幂等范围与关键防重状态的可靠性、并发、补偿/人工处置是否覆盖所需业务保证。不能仅凭“使用了消息队列”就认定业务只会生效一次。 |
| D07 | 批量与异步处理 | 业务日/自然日、作业先后、重跑/补跑、部分成功、重复/乱序/迟到、失败队列、核对与恢复是否有明确定义。区分设计希望保证的顺序与实际上可实现的顺序。 |
| D08 | 性能与容量 | 请求类型、峰值、响应百分位、增长假设、资源/连接上限和扩展机制是否支持目标；计算同一路径上的顺序耗时及重试预算，保留并行/排队/观测不确定性。 |
| D09 | 可用性与恢复 | 故障检测、隔离、降级、单点、备份恢复、恢复时长和可接受数据损失是否匹配目标；复制不是备份，备份存在不证明可恢复。 |
| D10 | 安全、权限与审计 | 信任边界、服务端鉴权、最小权限、敏感信息保护、密钥、审计主体/对象/结果是否覆盖明确需求。脱敏展示与底层授权是不同控制。 |
| D11 | 部署、资源与依赖 | 逻辑组件如何映射部署单元、环境、网络及主要资源；外部依赖不可用时如何处理，逻辑双实例是否仍共享故障域。不能仅因总体架构图未展示物理部署细节，就直接判定存在单点故障。 |
| D12 | 可观测与运维 | 请求/消息/作业关联、指标告警、排障与人工修复入口、发布兼容及维护是否能支撑操作；应分别判断是否有日志，以及日志是否足以定位问题。 |
| D13 | 选型与演进 | 选型替代方案、复杂度/成本/能力匹配、升级约束、迁移过渡与旧方案退出是否有依据；不把偏好当硬约束，也不要求每个简单组件都长篇比较。 |
| D14 | 内部一致性 | 同一语境下图文/章节/术语/数量/方向/边界是否相容。单独看合理、放在一起却矛盾的陈述，要引用双方；不同视图粒度或不同版本不是天然冲突。 |
| D15 | 功能模块分解与需求分配 | 关键功能是否有承担模块、输入输出及协作边界；是否存在需求无人承担、关键功能漏分配、职责不清或重复分配责任。模块技术名称不必与需求标题逐字相同。 |
| D16 | 关键规则、主流程与状态 | 方案是否交代关键规则的适用条件/优先级、跨模块主流程及关键输入输出、重要状态转移和异常处理的最终结果及责任归属；不可将决定全局正确性的规则全部留到详细设计阶段再确定；模块内部的完整分支和产品细则可后续细化。 |
| D17 | 设计粒度与可细化性 | 按对职责边界、跨系统约定、数据权威/事务、信任/故障范围和关键质量目标的影响判断。已明确关键方案/约束、局部实现合理留到详细设计的文档可通过；不能仅因缺少方法签名、全量字段或 DDL、逐节点配置、完整脚本，就判定内容缺失。若项目明确要求本阶段给出，按该要求审查。 |

## 判断与分级

确定故障路径和业务影响后分级：`critical` 需要材料能支持大范围且不可逆的影响；`high` 为关键流程失败或重大数据/访问问题；`medium` 为局部失败、重要歧义或可恢复风险；`low` 为影响有限的维护/表达问题。缺证本身不自动 critical/high；如缺证妨碍关键决策，可说明潜在影响并保持证据强度 insufficient。

使用最直接的主维度，必要时在正文注明关联维度。同一根因不要以 D04、D06、D09 重复计三个问题。对时间或数量边界必须核对单位、比较符号、并发与统计窗口。

## 简短对照

- 明确要求投产前提供恢复方案，但当前最终稿没有该项：D09 omission，指出需求和缺项。
- 文件引用《恢复专题》但未给出：通常为 D09 evidence_gap/未审，不声称系统没有备份。
- 主站与备站共用故障点且违背已明确故障域目标：D09 risk 或 conflict，说明目标和共同依赖。
- 过渡阶段保留同步调用且有批准范围与退出条件：记录例外/阶段安排，不报“目标不一致”。
