# 概要设计内容要求（最终版）

适用技能：**概要设计检查助手**。版本日期：2026-11-10。

## 适用原则

**概要设计承载架构设计中结构性、全局性的部分：确定系统由什么组成、各部分承担什么职责、如何协作，以及共同遵守哪些关键规则和约束。** 它应形成可供各团队开展详细设计的共同基线。

本要求是内容覆盖清单，不是文档目录模板。章节名称、数量、顺序、分册方式及表达形式由项目决定；同一内容可以分散在文字、图表或明确版本的专题中，不要求同名章节或重复描述。应用、数据、技术、安全、集成与运维是五个检查视角，目标、约束、决策和验证贯穿其中。

总体概要设计应判断各检查视角是否适用；专题设计只覆盖约定范围，并明确与总体设计及其他专题的关系。条件场景不存在时说明不适用。合同、已批准需求、项目约定及适用制度有明确交付要求时，按其执行并标明依据；本清单本身不代表法规或强制标准。

## 深度边界

一项内容应在概设中明确，通常因为它会影响以下至少一项：

- 系统、模块、服务或平台之间的划分、职责及依赖。
- 多个模块或系统共同遵守的业务语义、状态、数据标准及协作规则。
- 数据权威来源、事务范围、信任边界、部署关系或故障影响范围。
- 关键性能、容量、可用性、安全目标及实现这些目标的总体机制。
- 重要技术取舍、跨团队约定、迁移切换或后续难以低成本调整的决定。

只影响单个模块内部、且不改变上述约定的实现选择，通常可留到详细设计。**判断依据是影响范围和决策重要性，不是某项内容是否带有“技术细节”。** 例如影响资金重复记账的防重规则、决定业务可否跨日的时间边界、决定容灾目标能否实现的复制约束，即使具体，也不能全部后移。

| 对比事项 | 概设应明确 | 可在详细设计或实施材料中说明 |
|---|---|---|
| 功能与处理 | 模块职责、关键场景、跨模块规则、重要状态和最终结果归属。 | 全部产品细则、类与方法设计、局部算法、完整页面与逐字段校验。 |
| 接口 | 集成关系、接口或服务能力范围、关键输入与输出结果、调用语义、兼容与异常处理原则。 | 每个报文字段、完整错误码、逐接口参数及接口文档全文。 |
| 数据库 | 主要对象关系、权威归属、数据分布、关键约束、事务和存储策略。 | 全部表列、完整DDL、逐表索引及具体SQL。 |
| 技术与部署 | 技术栈及关键兼容基线、部署单元与网络关系、故障边界、容量依据及扩展方式。 | 不影响架构的补丁版本、逐台主机IP、端口和配置参数。 |
| 运行与验证 | 发布及恢复策略、在途业务处理原则、监控责任、验证场景与通过条件。 | 流水线脚本、逐步操作手册、全部告警阈值及完整测试用例。 |

上述可后移内容若直接决定架构方案成立，或项目明确要求本阶段提交，应提前明确相应关键部分；不因此要求同类全部细节提前完成。

## 目标、范围与共同约束

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| G01 | 版本、范围与依据 | 文档及需求基线、设计阶段、本期边界；区分现状、目标、过渡态与已批准例外。说明关键依据的适用性，不按修改时间推断权威。 |
| G02 | 业务目标与关键要求 | 主要使用方、核心场景、重要功能与质量目标；可验证的指标口径、场景和约束。关键要求应能对应到负责实现它的模块或系统。 |
| G03 | 总体方案与重要取舍 | 系统在企业架构中的位置、主要组成及联系、沿用和新建边界；重要方案的选择理由、代价及主要替代方案。无需逐组件长篇比选。 |
| G04 | 假设、依赖与责任 | 上下游、公共平台、供应商和项目团队各自承担什么；依赖哪些外部能力与前提，前提未成立会影响哪些决定。 |

## 应用架构覆盖要求

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| AP01 | 功能分解与职责分配 | 重要业务及支撑能力由哪些模块承担，模块边界、主要输入输出和协作关系；关键功能均有明确的承担方，避免职责不清或多个模块争用同一项最终决定权。 |
| AP02 | 关键业务规则与不变量 | 影响模块划分、跨系统结果或业务正确性的规则及优先关系；关键参数的权威来源和生效边界。例如资金、额度、业务日期及状态的共同约束。 |
| AP03 | 核心流程与重要状态 | 代表性端到端场景中的参与方、主要阶段和状态；成功、拒绝、部分成功、超时或结果未知时，谁确认最终结果、如何继续处理。无需展开每条分支。 |
| AP04 | 应用集成关系 | 系统与模块的调用方、提供方、交互方向及目的；同步、异步、文件或事件方式的选用，业务处理与数据供给的职责边界。 |
| AP05 | 接口总体设计 | 对外及关键内部接口或服务能力的范围、关键输入与输出结果、业务语义、版本兼容原则；跨系统超时、防重、错误和最终结果查询的共同约定。接口过多时可分类并引用契约清单。 |
| AP06 | 批量、异步与日切〔有场景时〕 | 在线与批量的分工和并行边界、业务日期的权威来源、关键任务依赖及完成判据；重复、乱序、迟到、重跑和补跑对业务结果的影响及责任。 |
| AP07 | 人工操作、界面与报表〔有场景时〕 | 主要角色与业务入口、影响系统协作的审批或人工处置；跨模块查询、统计口径与权限边界。只需说明影响总体方案的交互。 |

可留后续：全部用例分支、页面原型、逐接口报文、完整产品规则和模块内部处理步骤。技术组件清单不能替代功能职责说明。

## 数据架构覆盖要求

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| DA01 | 数据对象与模型 | 主要数据域、业务对象、关键标识、关系及关键完整性约束，能支撑核心场景；可通过概念模型或必要的逻辑模型表达。 |
| DA02 | 数据权威来源与分布 | 主数据、业务数据和关键配置由谁维护，谁可写、谁使用副本；跨模块、库、法人或地域的分布方式及共享、隔离边界，避免多个未经协调的权威来源。 |
| DA03 | 数据通信与传输 | 主要数据从哪里到哪里、传什么、如何传、多久可用；同步或批量的时效和一致性要求，失败补传、重复处理、核对及责任分工。安全控制统一引用安全要求。 |
| DA04 | 数据标准与质量 | 全局共享的标识、编码、金额精度与单位、日期时区、字典和元数据的统一依据；跨系统标准映射及重要质量规则由谁维护和变更。无需抄录完整字段字典。 |
| DA05 | 数据库总体设计 | 数据库或存储的划分、选用类型、共享与隔离方式，以及主要对象到存储的映射；关键读写模式、事务边界及必要的分片、分区、冷热分层原则。具体策略按实际规模选择。 |
| DA06 | 容量与生命周期 | 关键数据量及增长假设，在线、历史和归档范围；留存依据、历史查询、冻结保留和清理的共同规则，以及副本、日志和备份之间的关系。 |
| DA07 | 数据迁移〔有场景时〕 | 源目标范围、总体转换与清洗策略、全量与增量衔接、新旧共存；完整性和业务核对、停止写入与增量追平的安排，以及切换后的回退边界和不可逆变更的处理原则。迁移脚本和逐字段映射可另行细化。 |

可留后续：全部物理表列、逐表索引、完整DDL、SQL、逐字段迁移映射与搬迁脚本。影响数据分布、账务关系或跨系统兼容的关键字段及约束，应在概设中明确。

## 技术架构覆盖要求

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| TE01 | 分层、技术栈与选型 | 主要技术层次、关键组件职责、运行平台和技术栈；重要版本系列或兼容基线、授权及既有平台约束。普通补丁版本可在后续冻结制品基线时确定，架构相关差异需提前说明。 |
| TE02 | 通用异常处理机制 | 业务拒绝、技术故障及结果未知的区别；端到端超时预算原则、可重试边界、防重、限流、熔断、降级和人工介入的全局机制及责任。无需逐接口穷举参数和错误码。 |
| TE03 | 事务、并发与一致性 | 核心场景的原子性范围、一致性目标及提交判据；跨模块并发、防重、补偿或冲正、未决状态和恢复原则。说明机制如何满足业务约束，不能只写产品名称。 |
| TE04 | 物理部署与依赖 | 主要部署单元与运行位置、中心或区域、网络和存储关系；逻辑组件如何落到部署单元、哪些资源共享、哪些依赖可能同时失效，及总体资源估算依据。 |
| TE05 | 性能、容量与扩展 | 关键业务组合、峰值与增长、响应时间等目标及其统计口径；瓶颈假设、资源估算、扩容和降级策略，适用时说明单中心接管能力。估算不等于性能已达标。 |
| TE06 | 高可用、灾备与恢复 | 适用故障场景下的检测、隔离、接管、回切及共同依赖；恢复时长RTO和允许数据损失RPO等目标与实现机制。按需要选择主备、双活或其他方式，不统一强制双活。 |
| TE07 | 分布式与共享状态〔有场景时〕 | 实际采用的注册配置、远程调用、消息、缓存、分布式事务、标识或调度等能力的分工；状态的权威来源、关键一致性、网络分区及恢复规则。不要求为了满足清单而引入无实际用途的组件。 |
| TE08 | 其他关键技术方案〔有场景时〕 | 对决定业务正确性或关键质量目标的特殊技术，说明适用场景、总体机制、约束及验证方式，如热点治理、大批量计算、规则执行或文件处理。 |

可留后续：模块内部的类、方法和算法设计、普通组件补丁清单、逐节点IP端口、全部中间件配置及性能调优参数。关系到整体正确性或目标可行性的关键机制及参数需提前给出。

## 安全架构覆盖要求

安全覆盖实际存在的数据生命周期与系统边界。各环节应说明保护对象、控制位置、依赖能力和责任，允许引用统一安全平台或专题；不要求重复配置同一控制，也不以一句“已加密”替代全部保护方案。

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| SE01 | 数据采集安全 | 来源及真实性、业务目的、必要范围和输入信任边界；涉及受保护信息时，明确适用处理依据与责任，不虚构统一授权方式。 |
| SE02 | 数据传输安全 | 跨信任边界的端点身份、认证授权、机密性和完整性保护；适用时说明防重放、证书与密钥依赖，覆盖实际接口、文件和管理通道。 |
| SE03 | 数据存储安全 | 数据分类对应的访问隔离、加密及密钥管理策略，覆盖在线、历史和备份；密钥轮换、禁用及恢复所依赖的能力和责任分工。 |
| SE04 | 数据处理安全 | 批量、临时文件、中间结果、缓存及日志等处理路径的保护；生产与非生产数据使用边界、脱敏或去标识化策略。 |
| SE05 | 数据使用安全 | 用户与服务身份、授权模型、最小权限、租户或法人及数据范围隔离；展示、查询、下载、导出和特权操作的控制与审计原则。 |
| SE06 | 数据交换安全 | 接收方、用途、范围、授权及接收确认；对外共享的后续使用约束与追溯责任。安全通道不能替代业务授权。 |
| SE07 | 数据销毁安全 | 到期、退役等销毁条件、审批责任、数据与副本范围、可验证的销毁策略；处理备份、缓存、日志与冻结保留的冲突。普通删除或归档不自动等于安全销毁。 |
| SE08 | 通用数据安全 | 分类分级、资产责任、统一权限与密钥生命周期、审计和安全事件处置的总体安排；留存及控制依据需确认适用性，不编造法定期限。 |
| SE09 | 系统与运行安全 | 数据安全之外的身份认证、网络和应用信任边界、凭证配置、组件来源与漏洞管理、环境隔离及特权运维控制；公共平台承担时写明接入和责任。 |

可留后续：逐用户权限表、全部接口权限点、完整安全规则配置及具体操作流程。涉及跨系统授权、敏感数据流向和关键控制能否生效的边界，应在概设中确定。

## 集成与运维覆盖要求

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| OP01 | 构建集成与系统联调 | 构建、制品和配置的版本可追溯原则、关键质量检查与通过条件；跨系统联调的范围、依赖环境、契约基线和责任。区分软件构建集成与应用间的业务集成，并说明两者如何衔接。 |
| OP02 | 部署、发布与回退 | 发布单元、关键依赖顺序、应用/配置/数据的兼容策略；切换或灰度原则、发布验证及通过条件及回退边界，特别是新业务已发生后的恢复处理。 |
| OP03 | 优雅启停与异常退出 | 启动依赖、就绪状态及开始接收请求的条件；停机时停止新请求、处理在途业务、保存必要状态的原则；与崩溃或强停后恢复机制衔接。无需逐进程启动命令。 |
| OP04 | 环境与配置管理 | 环境的用途和隔离、关键差异、共享资源及访问边界；配置变更、生效和版本责任，引用非生产数据安全要求。无需完整主机台账。 |
| OP05 | 监控、日志与告警 | 关键业务与技术状态如何观测，请求、消息、批任务如何关联；日志分类、敏感信息保护与留存原则，以及告警到处置的责任。具体格式和常规阈值可后续配置。 |
| OP06 | 备份与恢复 | 必要数据、配置、文件和密钥的保护范围，满足RTO/RPO的备份及恢复策略、独立性和依赖顺序；演练、校验及业务核对责任。复制不能替代备份。 |
| OP07 | 归档、清理与销毁 | 与数据留存及安全销毁规则相容的执行原则；清理前核验、失败暂停、冻结例外及追溯责任，避免清理破坏查询或恢复能力。 |
| OP08 | 运维职责与应急 | 日常作业、批量重跑、人工修复、故障升级和应急的责任边界；重要操作的授权、结果核对及连续性要求。详细步骤可放运行手册。 |

可留后续：流水线和安装脚本、逐台配置、备份计划明细、全部告警阈值、逐步启停及故障处置手册。概设需保证运行策略与架构、业务状态和恢复目标相容。

## 决策、验证与交付要求

| 编号 | 覆盖内容 | 概要层必须明确 |
|---|---|---|
| V01 | 关键要求的验证 | 关键功能和质量目标对应哪些设计与验证场景，如何判定通过、谁负责；对重大技术不确定性说明必要的验证或原型安排。本阶段不默认要求全部测试完成。 |
| V02 | 全局一致性 | 功能职责、接口语义、数据权威来源、状态、部署、故障恢复和安全规则相互一致；相同对象在文字、图表和分册中的版本、数量、方向及术语一致。 |
| V03 | 决策、风险与未决项 | 重要取舍、影响和已批准例外；未决事项注明责任人、依赖、影响范围及完成条件，区分可后续细化和阻碍当前方案成立的事项。关键未决不能仅写“后续考虑”。 |
| V04 | 引用与后续设计衔接 | 专题、接口契约、数据库或迁移设计等的名称、版本、承担内容、责任及交付安排；说明已审和未审范围，后续设计应遵守哪些已确定的全局约束。 |

## 跨领域内容如何衔接

以下是责任划分示例，不是章节要求。一个决定在某处明确后，其他相关位置引用并保持一致即可。

| 主题 | 需要相互衔接的内容 |
|---|---|
| 集成与接口 | 应用说明业务关系和契约；数据架构说明数据供给及一致性要求；技术说明通信机制；安全说明保护；运维说明联调、观测与恢复责任。 |
| 数据库 | 数据说明模型、归属和分布；技术说明产品及拓扑约束；安全架构说明授权及密钥管理；运维说明变更和恢复。 |
| 异常与恢复 | 应用说明业务状态及最终结果；技术说明超时、防重、补偿等机制；运维说明发现、介入和核对责任。 |
| 部署与发布 | 技术说明部署关系、依赖和故障影响；运维说明兼容、切换、回退和验证；安全说明信任边界。 |
| 留存与销毁 | 数据说明保留及退出规则；安全说明销毁授权与效果；运维说明执行、核验和失败处理。 |

## 编写与检查的完成标准

内容完整，指适用范围内的关键结构、全局约定、约束和重要决策有交代，并且互相一致、可验证；不以篇幅、章节数量、图示数量或实现细节的多少判断是否完整。

建议记录“覆盖项编号／适用性及理由／对应位置或专题版本／覆盖结论／待补充内容、责任人及完成条件”。位置可以是任意章节、表格或图示。采用文字、表格或图示时，能清楚表达相关关系即可，不强制每类图单独提供。

- 已覆盖：有足够说明或可核对的有效引用，能够约束后续详细设计。
- 需补充：有明确适用依据，应在本阶段确定的结构性或全局性内容尚未说明。
- 待确认／未审：关键事实、引用专题或可读证据尚缺，记录验证限制；不能据此断言系统没有该能力。
- 不适用：相关场景不在范围，或由其他已明确责任的设计承担，并说明理由。

检查时不因缺少同名章节报问题，不因没有完整字段、DDL、类与方法设计或操作脚本机械判缺项；也不能以“详细设计再定”为由推迟职责、数据权威来源、关键状态、资金一致性或恢复边界等决定。相同根因跨领域只记录一次。

设计充分、引用可核对、关键冲突已解决且未决项不妨碍当前基线成立时，可在本阶段通过；若全局方案仍依赖未经确认的关键假设，应明确待决条件与对评审结论的影响，不能仅凭清单是否勾选完成作出判断。

涉及银行资金业务时，按实际范围加查记账与余额、冻结与可用性、冲正与对账、跨日未决、法人隔离、关键参数生效，以及交易/批量/外围接口在切换恢复时的一致性。这些是全局业务约束，不要求把全部产品明细前移到概设。

本要求用于文档编写与概要评审，不等于实现已正确、测试已通过或已获得合规认证。
